## A. Gesture detection on a home screen

### A1. Platform gesture detectors

**What's possible.** Single-pointer taps, double taps, long-press, scroll and fling via `GestureDetector`; two-finger pinch via `ScaleGestureDetector`; anything else (multi-finger swipes, two-finger double-tap, edge swipes) via raw `MotionEvent` handling.

**Exact API bits.**
- `android.view.GestureDetector`: "Detects various gestures and events using the supplied MotionEvents. The OnGestureListener callback will notify users when a particular motion event has occurred. This class should only be used with MotionEvents reported via touch (don't use for trackball events)." Usage: "In the View.onTouchEvent(MotionEvent) method ensure you call onTouchEvent(MotionEvent)"; for context clicks "you must call onGenericMotionEvent(MotionEvent) in View.onGenericMotionEvent(MotionEvent)" (https://developer.android.com/reference/android/view/GestureDetector). `onTouchEvent` API 1; `onGenericMotionEvent` API 23; `setContextClickListener` API 23; `setOnDoubleTapListener` API 3; `setIsLongpressEnabled` API 1: "if this is enabled when a user presses and holds down you get a longpress event and nothing further. If it's disabled the user can press and hold down and then later moved their finger and you will get scroll events. By default longpress is enabled." Callbacks: `OnGestureListener` (onDown, onShowPress, onSingleTapUp, onScroll, onLongPress, onFling), `OnDoubleTapListener` (onSingleTapConfirmed, onDoubleTap, onDoubleTapEvent), `OnContextClickListener.onContextClick`.
- `android.view.ScaleGestureDetector`: detects two-finger scaling; `getScaleFactor()`, `getCurrentSpan()`; quick-scale (`setQuickScaleEnabled`) API 19; stylus scale (`setStylusScaleEnabled`) API 31 (https://developer.android.com/reference/android/view/ScaleGestureDetector — API levels taken from the reference page summary).
- `android.view.ViewConfiguration` (https://developer.android.com/reference/android/view/ViewConfiguration), all verified verbatim:
  - `getScaledTouchSlop()` API 3 — "Distance in pixels a touch can wander before we think the user is scrolling".
  - `getScaledPagingTouchSlop()` API 8 — "…before we think the user is scrolling a full page".
  - `getScaledDoubleTapSlop()` API 3 — "Distance in pixels between the first touch and second touch to still be considered a double tap".
  - `getScaledEdgeSlop()` API 3 — "Inset in pixels to look for touchable content when the user touches the edge of the screen".
  - `getScaledMinimumFlingVelocity()` API 3 / `getScaledMaximumFlingVelocity()` API 4 — "Minimum/Maximum velocity to initiate a fling, as measured in pixels per second"; per-input-device overloads `(int inputDeviceId, int axis, int source)` API 34.
  - `getLongPressTimeout()` API 1 (static) — "Used for both key and motion events… the duration in milliseconds before a press turns into a long press"; `getDoubleTapTimeout()` API 3 (static); `getTapTimeout()` API 1 (static) — "the duration in milliseconds we will wait to see if a touch event is a tap or a scroll". Instance variants `getLongPressTimeoutMillis()`, `getDoubleTapTimeoutMillis()`, `getTapTimeoutMillis()` are "Added in version 36.1".
  - `getScaledMinimumScalingSpan()` API 29 — "distance in pixels between touches that must be reached for a gesture to be interpreted as scaling".
  - `getScaledAmbiguousGestureMultiplier()` API 30 — "If a MotionEvent has MotionEvent.CLASSIFICATION_AMBIGUOUS_GESTURE set, then certain actions, such as scrolling, will be inhibited. However… existing gesture thresholds (e.g. scrolling touch slop and the long-press timeout) should be scaled by this factor".
  - `getScaledHandwritingSlop()` API 34.
- `android.view.MotionEvent` (https://developer.android.com/reference/android/view/MotionEvent): multi-touch via `getPointerCount()`, `getActionMasked()`, `ACTION_POINTER_DOWN/UP`, `getActionIndex()`, `getPointerId()`, `findPointerIndex()`, `getX(int)`. `getClassification()` API 29: "The classification may change as more events become available for the same gesture." Constants: `CLASSIFICATION_NONE` (0), `CLASSIFICATION_AMBIGUOUS_GESTURE` (1) "Gestural actions, such as scrolling, should be inhibited until the classification resolves", `CLASSIFICATION_DEEP_PRESS` (2) "should be used to accelerate the long press behaviour" — all API 29; `CLASSIFICATION_TWO_FINGER_SWIPE` (3) and `CLASSIFICATION_PINCH` (5) API 34 are touchpad-only ("touchpad scroll", "touchpad pinch"). Edge flags: `getEdgeFlags()` API 1 — "Returns a bitfield indicating which edges, if any, were touched by this MotionEvent… This property is only set for ACTION_DOWN events."; `EDGE_LEFT/RIGHT/TOP/BOTTOM` API 1.

**Constraints and gotchas.**
- `GestureDetector` is single-pointer oriented (the class contract speaks only of touch `MotionEvent`s; it has no pointer-count aware callbacks). Multi-finger swipes and two-finger double-tap must be hand-rolled from `ACTION_POINTER_DOWN/UP` + per-pointer coordinates + a `VelocityTracker`, using the `ViewConfiguration` thresholds above rather than hard-coded px.
- Edge detection: `getEdgeFlags()` is set only on `ACTION_DOWN`; on gesture-nav devices the system consumes most edge swipes anyway (A2).
- Deep-press classification (API 29) lets you fire long-press early; ambiguous classification asks you to widen slop.

**Implication for justa-launcher:** implement one custom `View.onTouchEvent` state machine (down → classify → fling/long-press/multi-tap) driven by `ViewConfiguration` values; reuse `GestureDetector` only for the trivial single-finger cases and `ScaleGestureDetector` for pinch; no library needed.

### A2. Conflicts with system gesture navigation (Android 10+)

**What's possible.** Side swipes near the left/right edge are the system back gesture; the bottom band is home/quick-switch and cannot be reclaimed. Apps can request priority over the back gesture in specific rects, and a **home activity is exempt from the usual 200 dp cap** on such exclusions.

**Exact API bits.**
- Gesture-nav guide (https://developer.android.com/develop/ui/views/touch-and-input/gestures/gesturenav): "The new system gesture for back is an inward swipe from either the left or the right edge of the screen." "The new system gestures for home and quick switch both involve swipes at the bottom of the screen in the space previously occupied by the nav bar. Apps can't opt out of these gestures as they can with the back gesture." "To mitigate this problem, Android 10 introduces the WindowInsets.getMandatorySystemGestureInsets() API, which informs apps of the touch recognition thresholds." Immersive mode: "This disables the system gestures while the user is interacting with the game, but lets the user re-enable the system gestures by swiping from the bottom of the screen."
- `View.setSystemGestureExclusionRects(List<Rect>)` API 29 (https://developer.android.com/reference/android/view/View): "Sets a list of areas within this view's post-layout coordinate space where the system should not intercept touch or other pointing device gestures. This method should be called by onLayout(boolean, int, int, int, int) or onDraw(Canvas). … It is not necessary for an app to register exclusion rects for broadly spanning regions such as the entirety of a ScrollView or for simple press and release click targets such as Button. Mark an exclusion rect when interacting with a view requires a precision touch gesture in a small area in either the X or Y dimension, such as an edge swipe or dragging a SeekBar thumb. **Note: the system will put a limit of 200dp on the vertical extent of the exclusions it takes into account. The limit does not apply while the navigation bar is stickily hidden, nor to the input method and home activity.**"
- `WindowInsets.Type` (API 30, https://developer.android.com/reference/android/view/WindowInsets.Type): `systemGestures()` — "The system gesture insets represent the area of a window where system gestures have priority and may consume some or all touch input, e.g. due to the a system bar occupying it, or it being reserved for touch-only gestures. Simple taps are guaranteed to reach the window even within the system gesture insets, as long as they are outside the system window insets." `mandatorySystemGestures()` — see `WindowInsets.getMandatorySystemGestureInsets()` (API 29, deprecated 30): "In contrast to regular system gestures, mandatory system gestures cannot be overridden by View.setSystemGestureExclusionRects." `tappableElement()` — see `getTappableElementInsets()`: "represent how much tappable elements must at least be inset to remain both tappable and visually unobstructed by persistent system windows. This may be smaller than getSystemWindowInsets() if the system window is largely transparent and lets through simple taps (but not necessarily more complex gestures)." `systemBars()` = "statusBars(), captionBar() as well as navigationBars(), systemOverlays(), but not ime()". `displayCutout()` API 30 note: with default `layoutInDisplayCutoutMode`, "WindowInsets.getDisplayCutout() will return null even if the window overlaps a display cutout area, in which case the displayCutout() inset will still report the accurate value." (https://developer.android.com/reference/android/view/WindowInsets)

**Constraints and gotchas.**
- Only the back-gesture zones can be excluded; bottom home/recents zone never. Mandatory insets cannot be overridden even by the home app.
- The 200 dp cap exemption for the home activity is explicit — a launcher can claim full-height left/right edge strips for its own edge swipes, but this defeats the user's back gesture inside the launcher (acceptable on Home, where back normally does nothing).
- Read `systemGestures()`/`mandatorySystemGestures()` insets at runtime and keep your own swipe start zones away from them, or accept that a left/right swipe starting inside the edge zone will be eaten by the system on gesture-nav devices; 3-button-nav devices have no such zone.

**Implication for justa-launcher:** treat horizontal swipes as "start anywhere except the mandatory gesture insets"; optionally expose a theme/setting to register edge exclusion rects (allowed full-height for a home app) for users who want in-launcher edge gestures.

### A3. Back handling and predictive back on a home activity

**What's possible / exact bits.**
- Predictive back introduced in Android 13; "Predictive back is enabled by default." for apps that do not intercept back (https://developer.android.com/guide/navigation/custom-back/predictive-back-gesture). "Starting with Android 15, the developer option for predictive back animations is no longer available. System animations such as back-to-home, cross-task, and cross-activity now appear for apps that have opted in to the predictive back gesture either entirely or at an activity level."
- Android 16 behavior change: "For apps targeting Android 16 (API level 36) or higher and running on an Android 16 or higher device, the predictive back system animations (back-to-home, cross-task, and cross-activity) are enabled by default. Additionally, onBackPressed is not called and KeyEvent.KEYCODE_BACK is not dispatched anymore. … temporarily opt out by setting the android:enableOnBackInvokedCallback attribute to false" (https://developer.android.com/about/versions/16/behavior-changes-16).
- `R.attr.enableOnBackInvokedCallback` API 33: "If false, KEYCODE_BACK and Activity.onBackPressed() and related event will be forwarded to the Activity and its views. If true, those events will be replaced by a call to OnBackInvokedCallback.onBackInvoked() on the focused window. By default, the behavior is configured by the same attribute in application." (https://developer.android.com/reference/android/R.attr)
- `Activity.onBackPressed()` API 5, deprecated API 33: "On platform versions prior to Build.VERSION_CODES.S, it finishes the current activity… Starting with platform version Build.VERSION_CODES.S, for activities that are the root activity of the task and also declare an IntentFilter with Intent.ACTION_MAIN and Intent.CATEGORY_LAUNCHER in the manifest, the current activity and its task will be moved to the back of the activity stack instead of being finished." (https://developer.android.com/reference/android/app/Activity)
- `OnBackInvokedDispatcher` (API 33): `registerOnBackInvokedCallback(priority, callback)`; `PRIORITY_DEFAULT` (0), `PRIORITY_OVERLAY` (1000000) API 33; `PRIORITY_SYSTEM_NAVIGATION_OBSERVER` API 36: "invoked only when a back event is not consumed by any other registered OnBackInvokedCallback… They are called when the system is about to perform its default back navigation action, such as finishing the current activity or executing a back-to-home animation. These callbacks are purely observational." (https://developer.android.com/reference/android/window/OnBackInvokedDispatcher)
- Guide: "KeyEvent.KEYCODE_BACK is not deprecated as there are some supported use cases…; however, intercepting back events from KeyEvent.KEYCODE_BACK is no longer supported."

**Constraints and gotchas.**
- No document states what the system does when back is invoked on the *home* task with no callback registered. From the `onBackPressed` contract, the default for a task-root launcher-category activity is "moved to the back of the activity stack" — for the home task this is effectively a no-op — but that text is about `onBackPressed`, and under predictive back the system performs its own default action. **UNVERIFIED**: exact ATMS behavior for back-on-home under predictive back.
- Safe design: register a `PRIORITY_DEFAULT` `OnBackInvokedCallback` on the home activity that closes in-launcher overlays (search, settings) and otherwise does nothing. A registered callback consumes back, so no system animation is attempted. Keep `android:enableOnBackInvokedCallback="true"` (default) so you don't fall on the deprecated `onBackPressed` path.

**Implication for justa-launcher:** never rely on `onBackPressed`/`KEYCODE_BACK`; route "back" through `OnBackInvokedDispatcher` (API 33+) with a compat fallback for API < 33, and use it only to dismiss search/overlays.

### A4. Haptics

**Exact API bits.**
- `View.performHapticFeedback(int)` API 3: "Provide haptic feedback to the user for this view. The framework will provide haptic feedback for some built in actions, such as long presses, but you may wish to provide feedback for your own widget. The feedback will only be performed if isHapticFeedbackEnabled() is true." `performHapticFeedback(int, int flags)` API 3. `performHapticFeedback(HapticFeedbackRequest)` "Added in version 36.1": "allows you to make more elaborate haptic feedback requests, including setting the usage type… The usage provided for this API must be of VibrationAttributes.USAGE_CLASS_FEEDBACK, or VibrationAttributes.USAGE_UNKNOWN. Otherwise, the haptic feedback will not be played." (https://developer.android.com/reference/android/view/View). The reference lists no permission for `performHapticFeedback`.
- `HapticFeedbackConstants` (https://developer.android.com/reference/android/view/HapticFeedbackConstants), API levels verified: `LONG_PRESS` 3, `VIRTUAL_KEY` 5, `KEYBOARD_TAP` 8, `CLOCK_TICK` 21, `CONTEXT_CLICK` 23, `KEYBOARD_PRESS` 27, `TEXT_HANDLE_MOVE` 27, `GESTURE_START` 30 ("The user has started a gesture (e.g. on the soft keyboard)"), `GESTURE_END` 30, `CONFIRM` 30 ("A haptic effect to signal the confirmation or successful completion of a user interaction"), `REJECT` 30, `TOGGLE_ON` 34, `TOGGLE_OFF` 34, `GESTURE_THRESHOLD_ACTIVATE` 34, `GESTURE_THRESHOLD_DEACTIVATE` 34, `DRAG_START` 34, `SEGMENT_TICK` 34, `SEGMENT_FREQUENT_TICK` 34 ("expected to be very soft"), `NO_HAPTICS` 34 ("Applications may use this value to indicate skipping a call to View.performHapticFeedback entirely"). `KEYBOARD_RELEASE`, `VIRTUAL_KEY_RELEASE` are API 27 per the page summary (not re-verified line by line). Flags: `FLAG_IGNORE_VIEW_SETTING`; `FLAG_IGNORE_GLOBAL_SETTING` deprecated API 33 ("Starting from Build.VERSION_CODES.TIRAMISU only privileged…"). Note: the brief's phrasing "Android 14 additions like CONFIRM/REJECT/GESTURE_START/GESTURE_END" is off — those are API 30; TOGGLE_ON/OFF, GESTURE_THRESHOLD_*, DRAG_START, SEGMENT_* and NO_HAPTICS are the API 34 additions.
- Direct vibration: `Context.VIBRATOR_SERVICE` deprecated API 31 — "Use VibratorManager to retrieve the default system vibrator." (https://developer.android.com/reference/android/content/Context); `VibratorManager` API 31, `getDefaultVibrator()`, `vibrate(CombinedVibration)` (https://developer.android.com/reference/android/os/VibratorManager); `Vibrator.vibrate(VibrationEffect)` API 26, `vibrate(VibrationEffect, VibrationAttributes)` API 33, `hasAmplitudeControl` 26, `areEffectsSupported/areAllEffectsSupported` 30 (https://developer.android.com/reference/android/os/Vibrator); `VibrationEffect.createPredefined(int)` API 29 with `EFFECT_CLICK` (0), `EFFECT_DOUBLE_CLICK` (1), `EFFECT_TICK` (2), `EFFECT_HEAVY_CLICK` (5), all API 29 — "Predefined effects are a set of common vibration effects that should be identical, regardless of the app they come from" (https://developer.android.com/reference/android/os/VibrationEffect). Permission `android.permission.VIBRATE` — "Protection level: normal" (https://developer.android.com/reference/android/Manifest.permission).

**Implication for justa-launcher:** use `View.performHapticFeedback` with `CONFIRM`/`REJECT`/`GESTURE_START/END` (API 30+) falling back to `LONG_PRESS`/`VIRTUAL_KEY`; it respects the user's system haptics setting and needs no permission. Only add `VIBRATE` + `VibrationEffect` if you want custom patterns.

### C2. Two architectures

**(1) Set SYSTEM wallpaper + transparent launcher window showing it.**
- Theme: `android:windowShowWallpaper` (attr API 5) — "Flag indicating that this window's background should be the user's current wallpaper. Corresponds to WindowManager.LayoutParams.FLAG_SHOW_WALLPAPER." (https://developer.android.com/reference/android/R.attr). `FLAG_SHOW_WALLPAPER` API 5: "ask that the system wallpaper be shown behind your window. The window surface must be translucent to be able to actually see the wallpaper behind it; this flag just ensures that the wallpaper surface will be there if this window actually has translucent regions. This flag can be controlled in your theme through the R.attr.windowShowWallpaper attribute; this attribute is automatically set for you in the standard wallpaper themes such as R.style.Theme_Wallpaper, R.style.Theme_Wallpaper_NoTitleBar, R.style.Theme_Wallpaper_NoTitleBar_Fullscreen, R.style.Theme_Holo_Wallpaper… R.style.Theme_DeviceDefault_Wallpaper" (https://developer.android.com/reference/android/view/WindowManager.LayoutParams). `Intent.ACTION_WALLPAPER_CHANGED` deprecated API 16: "Modern applications should use WindowManager.LayoutParams.FLAG_SHOW_WALLPAPER to have the wallpaper shown behind their UI, rather than watching for this broadcast and rendering the wallpaper on their own."
- Pros: zero image memory in the launcher process (the wallpaper service owns the bitmap); parallax via offsets; system-wide theming (`WallpaperColors`, Monet) follows the image; lock screen can share it (`FLAG_SYSTEM|FLAG_LOCK`).
- Cons: needs `SET_WALLPAPER` (normal); each rotation rewrites persistent storage as PNG/JPEG and broadcasts `ACTION_WALLPAPER_CHANGED`; setting FLAG_SYSTEM only splits a shared wallpaper into lock-only (quoted above) — user-visible side effect; replaces the user's live wallpaper; the launcher can never read the current wallpaper back (Android 13+, above); `isSetWallpaperAllowed()` may be false under device policy; `getWallpaperColors()` must be off-main-thread.

**(2) Draw the image in the launcher's own window.**
- No permission, no lock-screen effect, no live-wallpaper conflict, deterministic; but the launcher process owns a screen-sized bitmap (≈ w×h×4 bytes for ARGB_8888, half for RGB_565; hardware bitmaps live in graphics memory — `Bitmap.Config.HARDWARE` API 26: "bitmap is stored only in graphic memory. Bitmaps in this configuration are always immutable. It is optimal for cases, when the only operation with the bitmap is to draw it on a screen." https://developer.android.com/reference/android/graphics/Bitmap.Config). You can still derive text-contrast hints locally with `WallpaperColors.fromBitmap()` (API 27). The window is opaque, so no need for `windowShowWallpaper`.

**Implication for justa-launcher:** offer both — default to (2) for reliability and privacy of the user's wallpaper choice, with an opt-in "also set as system/lock wallpaper" that uses `setStream(..., which)` and respects `isWallpaperSupported/isSetWallpaperAllowed`.

### C4. Fetching and decoding

- `HttpURLConnection` (https://developer.android.com/reference/java/net/HttpURLConnection): "HttpURLConnection will follow up to five HTTP redirects. - Cleartext: "Starting with Android 9 (API level 28), cleartext support is disabled by default." - Data Saver / metered: `ConnectivityManager.getRestrictBackgroundStatus()` API 24 with `RESTRICT_BACKGROUND_STATUS_DISABLED` (1), `WHITELISTED` (2) "application should take action to mitigate metered network access", `ENABLED` (3) "application should not try to use the network while running on background, because it would be denied"; `ACTION_RESTRICT_BACKGROUND_CHANGED` API 24 — "only sent to registered receivers, not manifest receivers"; `isActiveNetworkMetered()` API 16 "Requires Manifest.permission.ACCESS_NETWORK_STATE" (https://developer.android.com/reference/android/net/ConnectivityManager). `NetworkCapabilities.NET_CAPABILITY_NOT_METERED` (11) API 21; `NET_CAPABILITY_TEMPORARILY_NOT_METERED` API 30 — "most apps should use NET_CAPABILITY_NOT_METERED instead" (https://developer.android.com/reference/android/net/NetworkCapabilities). `INTERNET`, `ACCESS_NETWORK_STATE` are normal permissions.

Without one, an error will result in an Exception being thrown"), `setAllocator` with `ALLOCATOR_DEFAULT` ("Will typically result in a Bitmap.Config.HARDWARE allocation, but may be software for small images"), `ALLOCATOR_HARDWARE`, `ALLOCATOR_SOFTWARE`; `setMemorySizePolicy(MEMORY_POLICY_LOW_RAM)` ("an opaque 8-bit image may be compressed into an Bitmap.Config.RGB_565 configuration"); `decodeBitmap` "may take several seconds to complete, so it should only be called from a worker thread"; `createSource(File)` API 28, `createSource(Callable<AssetFileDescriptor>)` API 29, `isMimeTypeSupported` API 29.
- Memory budgets: `ActivityManager.getMemoryClass()` API 5 ("baseline Android memory class is 16"), `getLargeMemoryClass()` API 11 (needs `android:largeHeap`), `isLowRamDevice()` API 19 ("generally means something with 1GB or less of RAM") (https://developer.android.com/reference/android/app/ActivityManager).
- Cache: `Context.getCacheDir()` — "The system will automatically delete files in this directory as disk space is needed elsewhere… Apps are strongly encouraged to keep their usage of cache space below the quota returned by StorageManager.getCacheQuotaBytes(java.util.UUID)… Apps require no extra permissions" (https://developer.android.com/reference/android/content/Context); `StorageManager.getCacheQuotaBytes(UUID)` — "This quota will change over time depending on how frequently the user interacts with your app" (https://developer.android.com/reference/android/os/storage/StorageManager; API level not re-verified — 26 expected).
- Formats (https://developer.android.com/media/platform/supported-formats): JPEG and PNG encode+decode; BMP/GIF decode; WebP decode Android 4.0+ with lossless/transparency 4.2.1+; HEIF decode Android 8.0+; AVIF — "Encoder and decoder are mandatory beginning with Android 14."
- Passing the stream straight to `setStream`: the docs say JPEG/PNG ("any format handled by BitmapRegionDecoder"); for WebP/HEIF/AVIF sources decode via `ImageDecoder` first and use `setBitmap` (which re-encodes to PNG per the API text).

**Implication for justa-launcher:** `HttpURLConnection` + `ImageDecoder.setTargetSize(display size)` + `ALLOCATOR_HARDWARE` for on-screen use, software decode only when you need `WallpaperColors.fromBitmap`; enforce HTTPS-only (no cleartext config), skip fetches when `getRestrictBackgroundStatus()==ENABLED` or the active network is metered (user setting), cap the cache under `getCacheQuotaBytes`.

## D. Typography & layout customization surfaces

### D1. Fonts

- **System families (AOSP main `fonts.xml`)**: families `sans-serif`, `sans-serif-condensed`, `sans-serif-smallcaps`, `serif`, `monospace`, `serif-monospace`, `casual`, `cursive`, `roboto-flex`, `source-sans-pro`; aliases `sans-serif-thin` (100), `sans-serif-light` (300), `sans-serif-medium` (500), `sans-serif-black` (900), `sans-serif-condensed-light/medium`, `serif-bold`, `sans-serif-monospace`→monospace, plus legacy names (`arial`, `helvetica`, `times`, `courier`, …) (https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/data/fonts/fonts.xml). The file header now says: "DEPRECATED: This XML file is no longer a source of the font files installed in the system… For the application developers: please stop reading this XML file and use android.graphics.fonts.SystemFonts#getAvailableFonts Java API… WARNING: Parsing of this file by third-party apps is not supported." `SystemFonts.getAvailableFonts()` API 29 — "Returns all available font files in the system." (https://developer.android.com/reference/android/graphics/fonts/SystemFonts). OEMs ship their own configs, so family availability varies; `Typeface.create(String familyName, int style)` API 1 — "If null is passed for the name, then the 'default' font will be chosen" (unknown names fall back silently) (https://developer.android.com/reference/android/graphics/Typeface).
- **Weights**: `Typeface.create(Typeface family, int weight, boolean italic)` API 28 with the 100–900 weight table; `getWeight()` API 28 (0–1000). `android:textFontWeight` attr API 28 ("Weight for the font used in the TextView. May be an integer value").
- **Bundled fonts**: `res/font/` + font-family XML (`<font android:fontStyle android:fontWeight android:font>`), `android:fontFamily="@font/…"`, `getResources().getFont()` API 26; AndroidX `ResourcesCompat.getFont` back to API 16 (https://developer.android.com/develop/ui/views/text-and-emoji/fonts-in-xml). APK cost is simply the sum of font files (no doc statement; each weight/style is a separate file unless you ship one variable font).
- **Downloadable Fonts**: "lets APIs request fonts from a provider application instead of bundling files into the app"; benefits "Reduces the app size"; provider authority `com.google.android.gms.fonts`, package `com.google.android.gms`; "A device must have Google Play services version 11 or higher to use the Google Fonts provider."; "You must provide a certificate when you request fonts through the AndroidX Core library."; "If font retrieval takes longer than expected, the system aborts the fetching process and uses the default font." (https://developer.android.com/develop/ui/views/text-and-emoji/downloadable-fonts). Requires `androidx.core` (latest 1.19.0, https://dl.google.com/dl/android/maven2/androidx/core/group-index.xml) and GMS — on GMS-less devices (e.g. de-Googled ROMs) the provider is absent and you get the fallback font.
- **User-provided font files**: `Typeface.Builder(File)` / `(FileDescriptor)` / `(AssetManager, String)` API 26; `setFontVariationSettings(String)`, `setWeight(int)` (1–1000), `setItalic`, `setTtcIndex`, `setFallback(String familyName)`; `build()` "May return null if some parameters are invalid" (https://developer.android.com/reference/android/graphics/Typeface.Builder). `Typeface.createFromFile(File|String)` API 4. `Typeface.CustomFallbackBuilder` API 29 — custom fallback chain up to 64 families (`getMaxCustomFallbackCount()` "guaranteed… greater than or equal to 64"), `setSystemFallback(String)` "You can specify generic font family names or OEM specific family names", built from `Font.Builder` (API 29; `setFontVariationSettings` API 29) and `FontFamily.Builder` (https://developer.android.com/reference/android/graphics/Typeface.CustomFallbackBuilder, https://developer.android.com/reference/android/graphics/fonts/Font.Builder). Picking the file: `Intent.ACTION_OPEN_DOCUMENT` API 19 — "All selected documents are returned to the calling application with persistable read and write permission grants. If you want to maintain access to the documents across device reboots, you need to explicitly take the persistable permissions using ContentResolver.takePersistableUriPermission(Uri,int)" (https://developer.android.com/reference/android/content/Intent); `takePersistableUriPermission` — "Only URI permissions granted with Intent.FLAG_GRANT_PERSISTABLE_URI_PERMISSION can be persisted" (https://developer.android.com/reference/android/content/ContentResolver). MIME types: RFC 8081 ("The 'font' Top-Level Media Type", Feb 2017) registers `font/ttf`, `font/otf`, `font/collection`, `font/woff`, `font/woff2`, `font/sfnt` and deprecates `application/x-font-ttf`, `application/font-sfnt`, `application/font-woff` (https://www.rfc-editor.org/rfc/rfc8081). Which MIME strings Android DocumentsProviders actually report for .ttf/.otf is **UNVERIFIED** — pass several via `EXTRA_MIME_TYPES` (`font/ttf`, `font/otf`, `font/sfnt`, `application/x-font-ttf`, `application/octet-stream`) or accept `*/*` and sniff.
- **Variable fonts / features**: `TextView.setFontVariationSettings(String)` API 26 — axis tags "must contain four ASCII characters and must be wrapped with single quotes… If a specified axis name is not defined in the font, the settings will be ignored" (e.g. `"'wdth' 150"`); attr `fontVariationSettings` API 28; `setFontFeatureSettings` API 21 (CSS `font-feature-settings` syntax) (https://developer.android.com/reference/android/widget/TextView).

**Implication for justa-launcher:** theme schema should accept (a) a system family name (validated against `SystemFonts`/known aliases with graceful fallback), (b) a user font file via SAF (persisted URI, loaded with `Typeface.Builder` + `setFallback("sans-serif")`), and optionally (c) a variable-font axis string; skip Downloadable Fonts (GMS + androidx.core dependency).

### D2. Sizing and text layout

- **sp vs dp / non-linear scaling**: Android 14 — "the system supports font scaling up to 200%… the system applies a nonlinear scaling curve… large text doesn't scale at the same rate as smaller text." "Use TypedValue.applyDimension() to convert from sp units to pixels, and use TypedValue.deriveDimension() to convert pixels to sp. These methods apply the appropriate nonlinear scaling curve automatically." "Avoid hardcoding equations using Configuration.fontScale or DisplayMetrics.scaledDensity… the scaledDensity field is no longer accurate." "Don't use sp units for padding… 4sp + 20sp might not equal 24sp." "Always define android:lineHeight using sp units instead of dp" (https://developer.android.com/about/versions/14/features). `Configuration.fontScale`: "The equation for font scaling is now non-linear; this coefficient is no longer used as a direct multiplier… It exists for informational purposes only." (https://developer.android.com/reference/android/content/res/Configuration). `TypedValue.applyDimension` API 1; `deriveDimension` API 34; aliases `convertDimensionToPixels`/`convertPixelsToDimension` API 34 (https://developer.android.com/reference/android/util/TypedValue).
- **TextView knobs** (https://developer.android.com/reference/android/widget/TextView): `setTextSize(int unit, float)` API 1 ("if this TextView has the auto-size feature enabled, then this function is no-op"); `setAutoSizeTextTypeUniformWithConfiguration(min,max,step,unit)` API 26; `setLineHeight(int px)` API 28 and `setLineHeight(int unit, float)` API 34 ("SP units are strongly recommended"); `setLetterSpacing(float em)` API 21 ("Typical values for slight expansion will be around 0.05"); `setFallbackLineSpacing` API 28 ("required to be true if text could be in languages like Burmese or Tibetan"); `setIncludeFontPadding` API 1 ("extra top and bottom padding to make room for accents… The default is true"); `setElegantTextHeight` API 21 — Android 15: attribute "becomes true by default" for apps targeting 35; Android 16: "deprecates the elegantTextHeight attribute, and the attribute will be ignored once your app targets Android 16"; `setBreakStrategy` API 23 (default HIGH_QUALITY; hyphenation "has performance impact"), `setHyphenationFrequency` API 23 (default NONE); `setUseBoundsForWidth` API 35 — "This value is true by default if the target API version is 35 or later" (prevents clipping of cursive/complex glyphs; A15 behavior change); `setShadowLayer(radius, dx, dy, color)` API 1.
- **Accessibility**: "each interactive UI element have a focusable area, or touch target size, of at least 48dpx48dp"; contrast: "If the text is smaller than 18sp, or if the text is bold and smaller than 14sp, use foreground and background colors that result in a color contrast ratio of at least 4.5:1. For all other text, set the color contrast ratio to at least 3:1." (https://developer.android.com/guide/topics/ui/accessibility/apps).

**Implication for justa-launcher:** store theme text sizes in sp and let the platform scale them; keep row height ≥ 48dp regardless of font size; expose letterSpacing, lineHeight (sp), weight and includeFontPadding as theme fields; avoid hyphenation (performance) and don't touch elegantTextHeight.

### D3. Legibility over images

- `Paint.setShadowLayer(radius, dx, dy, color)` API 1 (long-color variant API 29): "Can be used to create a blurred shadow underneath text. Support for use with other drawing operations is constrained to the software rendering pipeline." (https://developer.android.com/reference/android/graphics/Paint) — text shadows are fine under hardware acceleration; `TextView.setShadowLayer` note: "The text shadow produced does not interact with… elevation and translationZ."
- Outline: `Paint.setStyle(Paint.Style.STROKE)` + `setStrokeWidth` ("Pass 0 to stroke in hairline mode") — draw text twice (stroke then fill) in a custom view; TextView has no outline attribute.
- Scrims: any gradient drawable behind the list; no API specifics.
- Auto text colour: `WallpaperColors.getColorHints() & HINT_SUPPORTS_DARK_TEXT` (API 31) — for your own image in architecture (2), compute `WallpaperColors.fromBitmap(bitmap)` (API 27) off the main thread and pick black/white text; for architecture (1), listen via `addOnColorsChangedListener` (API 27).

**Implication for justa-launcher:** ship three theme-selectable legibility modes — shadow (cheap, default), outline (custom view), scrim — and an "auto" text colour driven by `WallpaperColors`.

(https://developer.android.com/about/versions/16/behavior-changes-16). `R.attr.windowOptOutEdgeToEdgeEnforcement` API 35 text (https://developer.android.com/reference/android/R.attr). ## E. Optional heavyweight customizations

### E1. App-widget hosting

- Host API: `AppWidgetHost(Context, int hostId)` — "provides the interaction with the AppWidget service for apps, like the home screen, that want to embed AppWidgets in their UI."; `allocateAppWidgetId()` API 3; `createView()` API 3 ("The AppWidgetHost retains a pointer to the newly-created View"); `startListening()` "Call this when your activity becomes visible, i.e. from onStart()"; `stopListening()` from `onStop()`; `deleteAppWidgetId`, `deleteHost`, `deleteAllHosts` API 3; `getAppWidgetIds()` API 26; `startAppWidgetConfigureActivityForResult` API 21 ("the provided app widget has to be bound for this method to work") (https://developer.android.com/reference/android/appwidget/AppWidgetHost).
- Binding: `AppWidgetManager.bindAppWidgetIdIfAllowed(int, ComponentName)` API 16 (with options API 17; with `UserHandle` API 21) — "You need the BIND_APPWIDGET permission or the user must have enabled binding widgets always for your component. Should be used by apps that host widgets; if this method returns false, call ACTION_APPWIDGET_BIND to request permission to bind"; `ACTION_APPWIDGET_BIND` API 16 with `EXTRA_APPWIDGET_ID`, `EXTRA_APPWIDGET_PROVIDER` (+ `_PROFILE`); `ACTION_APPWIDGET_CONFIGURE` API 3 ("If you return Activity.RESULT_OK… the AppWidget will be added"); `getInstalledProvidersForProfile(UserHandle)` API 21; `ACTION_APPWIDGET_PICK` API 3 (https://developer.android.com/reference/android/appwidget/AppWidgetManager).
- **Does the default launcher get bind permission automatically? No.** `BIND_APPWIDGET` is declared `android:protectionLevel="signature|privileged"` with the comment "Not for use by third-party applications" (https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/core/res/AndroidManifest.xml). The service checks `enforceCallingOrSelfPermission(BIND_APPWIDGET)` and otherwise `isCallerBindAppWidgetAllowListedLocked` → `mPackagesWithBindWidgetPermission.contains(packageId)`; that allowlist is only mutated by `setBindAppWidgetPermission`, which requires `MODIFY_APPWIDGET_BIND_PERMISSIONS` (`signature|privileged`, `@SystemApi @hide`) — i.e. only the system's bind-confirmation UI can grant it (https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/services/appwidget/java/com/android/server/appwidget/AppWidgetServiceImpl.java). Nothing keys on `ROLE_HOME`. So every third-party launcher must go through the `ACTION_APPWIDGET_BIND` dialog once (the user can tick "always allow").
- Cost: `RemoteViews` inflation per widget, `AppWidgetHostView` lifecycle, listening for updates, size options bundles (Android 12 `targetCellWidth/Height`, `updateAppWidgetSize`), the host guide recommends limiting `RemoteViews` to `MAX_INIT_VIEW_COUNT` (16) (https://developer.android.com/develop/ui/views/appwidgets/host — via page summary).

**Implication for justa-launcher:** widget hosting contradicts "text-only, lightweight" — it brings foreign views, memory and a permission dialog; if ever added, gate it behind a single optional "widget page" and keep it out of the core module.

### E2. App shortcuts (static/dynamic/pinned)

- `LauncherApps.hasShortcutHostPermission()` API 25 — "Access is currently available to: The current launcher (or default launcher if there is no set current launcher). The currently active voice interaction service. Note when this method returns false, it may be a temporary situation because the user is trying a new launcher application…"; `getShortcuts(ShortcutQuery, UserHandle)` API 25 ("Callers must be allowed to access the shortcut information"); `startShortcut(...)` API 25; `pinShortcuts(...)` API 25 — "This API is NOT cumulative; this will replace all pinned shortcuts for the package. However, different launchers may have different set of pinned shortcuts."; `LauncherApps.Callback.onShortcutsChanged` API 25 ("Only the applications that are allowed to access the shortcut information… will receive it"); `registerCallback` API 21 (https://developer.android.com/reference/android/content/pm/LauncherApps, https://developer.android.com/reference/android/content/pm/LauncherApps.Callback). `ShortcutQuery`: `FLAG_MATCH_DYNAMIC` (1), `FLAG_MATCH_PINNED` (2), `FLAG_MATCH_MANIFEST` (8) API 25, `FLAG_MATCH_CACHED` (16) API 30, `FLAG_MATCH_PINNED_BY_ANY_LAUNCHER` API 28 (assistant/system only — "If you're a regular launcher app, there's no way to get shortcuts pinned by other launchers"), `FLAG_GET_KEY_FIELDS_ONLY` API 25 (cheap cache-refresh), `setPackage`, `setChangedSince` (https://developer.android.com/reference/android/content/pm/LauncherApps.ShortcutQuery).

**Feasibility in a text-only UI:** high — a long-press on an app name can list `ShortcutInfo` short labels as plain text rows and launch via `startShortcut`; no icons needed; works only while you are the default launcher, so degrade gracefully when `hasShortcutHostPermission()` is false.

**Implication for justa-launcher:** implement shortcuts as an optional text sub-menu (API 25+); skip pinning (adds state you must persist) unless users ask.

### E3. Icons
Not applicable to a text-only launcher; adaptive/themed icon APIs skipped.
