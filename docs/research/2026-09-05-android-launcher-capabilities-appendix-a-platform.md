## A. Being a home app

### A1. Manifest: the home intent filter and the attributes AOSP Launcher3 uses

**What is possible.** Any app can declare an activity handling `ACTION_MAIN` + `CATEGORY_HOME` + `CATEGORY_DEFAULT`; the user (or RoleManager) selects it as the default home.

**Exact bits — the AOSP Launcher3 home activity** (https://android.googlesource.com/platform/packages/apps/Launcher3/+/refs/heads/main/AndroidManifest.xml?format=TEXT, decoded):

```xml
<activity
    android:name="com.android.launcher3.Launcher"
    android:launchMode="singleTask"
    android:clearTaskOnLaunch="true"
    android:stateNotNeeded="true"
    android:windowSoftInputMode="adjustPan"
    android:screenOrientation="unspecified"
    android:configChanges="keyboard|keyboardHidden|mcc|mnc|navigation|orientation|screenSize|screenLayout|smallestScreenSize"
    android:resizeableActivity="true"
    android:resumeWhilePausing="true"
    android:taskAffinity=""
    android:exported="true"
    android:enabled="true">
    <intent-filter>
        <action android:name="android.intent.action.MAIN" />
        <action android:name="android.intent.action.SHOW_WORK_APPS" />
        <category android:name="android.intent.category.HOME" />
        <category android:name="android.intent.category.DEFAULT" />
        <category android:name="android.intent.category.MONKEY"/>
        <category android:name="android.intent.category.LAUNCHER_APP" />
    </intent-filter>
    <meta-data android:name="com.android.launcher3.grid.control" android:value="${packageName}.grid_control" />
</activity>
```

Launcher3's shared manifest (https://android.googlesource.com/platform/packages/apps/Launcher3/+/refs/heads/main/AndroidManifest-common.xml?format=TEXT) declares `CALL_PHONE`, `SET_WALLPAPER`, `SET_WALLPAPER_HINTS`, `BIND_APPWIDGET`, `READ_EXTERNAL_STORAGE`, `RECEIVE_BOOT_COMPLETED`, `REQUEST_DELETE_PACKAGES`, `READ_DEVICE_CONFIG`, `QUERY_ALL_PACKAGES`, `VIBRATE`, `ROTATE_SURFACE_FLINGER`, `WAKEUP_SURFACE_FLINGER`, `POST_NOTIFICATIONS`, its own `READ/WRITE_SETTINGS`, and a `NotificationListener` service guarded by `android.permission.BIND_NOTIFICATION_LISTENER_SERVICE` with the `android.service.notification.NotificationListenerService` intent filter. Note that Launcher3 is a system app; several of these (`ROTATE_SURFACE_FLINGER`, `WAKEUP_SURFACE_FLINGER`, `READ_DEVICE_CONFIG`, `BIND_APPWIDGET`) are not grantable to third-party apps.

Olauncher's real-world third-party equivalent (https://raw.githubusercontent.com/tanujnotes/Olauncher/master/app/src/main/AndroidManifest.xml): `MainActivity` with `launchMode="singleTask"`, `taskAffinity=""`, `excludeFromRecents="true"`, `windowSoftInputMode="stateAlwaysHidden"`, `configChanges="uiMode"`, `exported="true"`, filter MAIN + HOME + DEFAULT + LAUNCHER; a disabled `FakeHomeActivity` duplicate (used to re-trigger the home chooser); permissions `SET_WALLPAPER`, `EXPAND_STATUS_BAR`, `QUERY_ALL_PACKAGES`, `REQUEST_DELETE_PACKAGES`, `INTERNET`, `com.android.alarm.permission.SET_ALARM`, `PACKAGE_USAGE_STATS`, `ACCESS_HIDDEN_PROFILES` ("Used for Private Space support on Android 15+").

**Why each attribute matters** (activity-element reference https://developer.android.com/guide/topics/manifest/activity-element unless noted):
- `launchMode="singleTask"`: "If an instance of the activity already exists and is at the root of the task, the system routes the intent to existing instance through a call to its onNewIntent() method, rather than creating a new one." Only one home task can exist; other activities may still be launched into that task (unlike `singleInstance`).
- `clearTaskOnLaunch="true"`: "every time users start the task, they are brought to its root activity regardless of what they were last doing in the task"; "This attribute is ignored if FLAG_ACTIVITY_RESET_TASK_IF_NEEDED isn't set." Prevents e.g. a widget-config or settings activity that landed in the home task from covering the home screen on the next Home press.
- `stateNotNeeded="true"`: "If this attribute is set to "true", onSaveInstanceState() might not be called, and onCreate() is passed null instead of the Bundle" — the launcher must be able to rebuild from persistent state, which also saves memory/IPC.
- `resumeWhilePausing="true"` (not documented on the activity-element page; AOSP `attrs_manifest.xml`, https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/core/res/res/values/attrs_manifest.xml): "Indicate that it is okay for this activity be resumed while the previous activity is in the process of pausing, without waiting for the previous pause to complete. Use this with caution: your activity can not acquire any exclusive resources (such as opening the camera or recording audio) when it launches, or it may conflict with the previous activity and fail. The default value of this attribute is false." — this is what makes Home feel instant.
- `configChanges=...`: "declaring a configuration with this attribute prevents the activity from restarting. Instead, the activity remains running and its onConfigurationChanged() method is called." `screenSize`/`smallestScreenSize` added API 13; `density` 24; `grammaticalGender` 34. Launcher3 does not list `locale`/`fontScale`/`uiMode`, so it restarts on those (labels/text size must be re-read anyway).
- `screenOrientation="unspecified"`: "Warning: ... the system ignores the following values of this attribute for apps that target Android 16 (API level 36)" on sw≥600dp displays (portrait, landscape, reverse*, sensor*, user*).
- `windowSoftInputMode="adjustPan"` (Launcher3) vs `stateAlwaysHidden` (Olauncher): controls whether the home layout is panned/resized when the search keyboard shows. See the Android 17 IME change in §F.
- `taskAffinity=""`: an empty affinity keeps other apps' activities from re-parenting into the home task (documented under `taskAffinity`/`allowTaskReparenting` on the same page; exact wording not captured).
- `excludeFromRecents` (Olauncher): "when this activity is the root activity of a new task, this attribute determines whether the task appears in the list of recent apps."
- `exported="true"`: required for any activity with an intent filter; Android 12+ fails installation when it is missing on filtered components (https://developer.android.com/about/versions/12/behavior-changes-12).
- `enableOnBackInvokedCallback`: "Set android:enableOnBackInvokedCallback=false to turn off predictive back animations at the activity level" (relevant from Android 16 targeting, §A3).
- `CATEGORY_HOME`: "This is the home activity, that is the first activity that is displayed when the device boots." `CATEGORY_LAUNCHER_APP` is `@hide` ("...serves as the launcher app from there the user can start other apps... we need to be able to distinguish the home app from these setup helpers") and `CATEGORY_HOME_MAIN` is `@hide`; `CATEGORY_SECONDARY_HOME` (public) is "The home activity shown on secondary displays" (https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/core/java/android/content/Intent.java; https://developer.android.com/reference/android/content/Intent). `ACTION_SHOW_WORK_APPS` (API 33): "Action to show the list of all work apps in the launcher. For example, shows the work apps folder or tab."
- `android.software.home_screen` is a *device* feature: `PackageManager.FEATURE_HOME_SCREEN` (API 18) = "The device supports a home screen that is replaceable by third party applications" (https://developer.android.com/reference/android/content/pm/PackageManager). CDD §3.8.1: "If device implementations allow third-party applications to replace the device home screen, they: [C-1-1] MUST declare the platform feature android.software.home_screen" and "[C-1-2] MUST return the AdaptiveIconDrawable object..." (Android 16 CDD https://source.android.com/docs/compatibility/16/android-16-cdd; identical opening in the Android 17 CDD https://source.android.com/docs/compatibility/17/android-17-cdd). Declare it with `<uses-feature android:name="android.software.home_screen" android:required="true"/>` if you want Play to hide the app on devices that do not permit third-party homes (the `required` semantics come from the uses-feature element; exact wording not re-read here — **UNVERIFIED**).

**Constraints / gotchas.** `clearTaskOnLaunch` depends on the launching intent carrying `FLAG_ACTIVITY_RESET_TASK_IF_NEEDED`; the system home intent construction I read (§A2) adds `FLAG_ACTIVITY_NEW_TASK` explicitly — whether the reset flag is applied elsewhere for the home task is **UNVERIFIED**. Launcher3 additionally uses `largeHeap`, `hardwareAccelerated`, and a backup agent in its `<application>` element (common manifest).

**Play policy.** None specific to the home filter. Android 12+ requires explicit `android:exported`.

**Implication for justa-launcher.** Copy Launcher3's activity attributes (`singleTask`, `clearTaskOnLaunch`, `stateNotNeeded`, `resumeWhilePausing`, empty `taskAffinity`, exported) and Olauncher's `excludeFromRecents="true"`; handle `configChanges` for size/orientation yourself and persist all state so `onCreate(null)` is cheap.

### A2. How the Home key reaches the launcher; Back; process priority; crashes

**Home key → launcher** (AOSP main): `PhoneWindowManager.launchHomeFromHotKey()` checks keyguard, then `startDockOrHome()` which calls `ActivityManager.getService().stopAppSwitches()`, `sendCloseSystemWindows(SYSTEM_DIALOG_REASON_HOME_KEY)`, tries a dock intent, then `mActivityTaskManagerInternal.startHomeOnDisplay(userId, startReason, displayId, true /* allowInstrumenting */, fromHomeKey)` (https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/services/core/java/com/android/server/policy/PhoneWindowManager.java). `ActivityTaskManagerService.getHomeIntent()` builds `new Intent(mTopAction, ...)` with `mTopAction = Intent.ACTION_MAIN` and `addCategory(Intent.CATEGORY_HOME)` (https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/services/core/java/com/android/server/wm/ActivityTaskManagerService.java). `RootWindowContainer.startHomeOnTaskDisplayArea()` resolves the home activity, sets the component, `homeIntent.setFlags(homeIntent.getFlags() | FLAG_ACTIVITY_NEW_TASK)`, adds `EXTRA_FROM_HOME_KEY` when it came from the key, and starts it (https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/services/core/java/com/android/server/wm/RootWindowContainer.java). With `singleTask`, the existing instance receives `onNewIntent()`; the reference notes "An activity can never receive a new intent in the resumed state. You can count on onResume() being called after this method" and "getIntent() still returns the original Intent" (https://developer.android.com/reference/android/app/Activity).

**Back in a home app.** `Activity.onBackPressed()` (deprecated API 33): "On platform versions prior to S, it finishes the current activity... Starting with platform version S, for activities that are the root activity of the task and also declare an IntentFilter with Intent.ACTION_MAIN and Intent.CATEGORY_LAUNCHER in the manifest, the current activity and its task will be moved to the back of the activity stack instead of being finished. Other activities will simply be finished." (https://developer.android.com/reference/android/app/Activity). The Android 12 change page states the same ("Root launcher activities are no longer finished on Back press", https://developer.android.com/about/versions/12/behavior-changes-all). Gotcha: the protection keys off `CATEGORY_LAUNCHER`, not `CATEGORY_HOME`; a HOME-only activity that lets the default `onBackPressed` run would be *finished*. From Android 13 the recommended path is `OnBackInvokedCallback`, and when targeting Android 16 predictive back is on by default and `onBackPressed()` is not called at all (§F).

**Process priority.** `ProcessList.java`: `HOME_APP_ADJ = 600` with the comment "This is a process holding the home application -- we want to try avoiding killing it, even if it would normally be in the background, because the user interacts with it so much." Neighbours: `PREVIOUS_APP_ADJ = 700`, `CACHED_APP_MIN_ADJ = 900`/`MAX 999`, `SERVICE_ADJ = 500`, `PERCEPTIBLE_APP_ADJ = 200`, `VISIBLE_APP_ADJ = 100`, `FOREGROUND_APP_ADJ = 0` (https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/services/core/java/com/android/server/am/ProcessList.java). `OomAdjuster`: `if (state.getCachedIsHomeProcess()) { if (adj > HOME_APP_ADJ) { adj = HOME_APP_ADJ; schedGroup = SCHED_GROUP_BACKGROUND; state.setAdjType("home"); ...` (https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/services/core/java/com/android/server/am/OomAdjuster.java). So the home process is kept above cached apps and the previous app but below services, and runs in the background scheduling group when not on screen.

**If the default launcher crashes.** `AppErrors.handleAppCrashLSPB`: "If the crashing process is what we consider to be the "home process" and it has been replaced by a third-party app, clear the package preferred activities from packages with a home activity running in the process to prevent a repeatedly crashing app from blocking the user to manually clear the list. if (proc.isHomeProcess() && proc.hasActivities() && (app.info.flags & FLAG_SYSTEM) == 0) { proc.clearPackagePreferredForHomeActivities(); }" (https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/services/core/java/com/android/server/am/AppErrors.java). In other words a crashing third-party home loses its "default" status so the user is not locked out.

**Implication for justa-launcher.** Handle Back yourself (do nothing / return to the home list) via `OnBackInvokedCallback`, never let the default finish the activity; keep steady-state memory minimal because the process is resident at adj 600 for the life of the session; keep the home activity crash-free — repeated crashes silently un-default the launcher.

### A3. Becoming / checking the default launcher

**Exact bits.** `RoleManager` (API 29): `ROLE_HOME` = `"android.app.role.HOME"` ("The name of the home role. See also: Intent.CATEGORY_HOME"); `isRoleAvailable(String)` "Check whether a role is available in the system."; `isRoleHeld(String)` "Check whether the calling application is holding a particular role."; `createRequestRoleIntent(String)` "Returns an Intent suitable for passing to startActivityForResult(Intent,int) which prompts the user to grant a role to this application. If the role is granted, the resultCode will be Activity.RESULT_OK, otherwise it will be Activity.RESULT_CANCELED." Class doc: "apps should not make assumption about the availability of roles. Instead, they should always query if the role is available using isRoleAvailable(String) before trying to do anything with it" (https://developer.android.com/reference/android/app/role/RoleManager). Fallbacks: `Settings.ACTION_HOME_SETTINGS` (API 21) "Show Home selection settings. If there are multiple activities that can satisfy the Intent.CATEGORY_HOME intent, this screen allows you to pick your preferred activity."; `Settings.ACTION_MANAGE_DEFAULT_APPS_SETTINGS` (API 24) (https://developer.android.com/reference/android/provider/Settings). CDD: "If device implementations report android.software.home_screen, they: [C-1-1] MUST honor the android.settings.HOME_SETTINGS intent to show a default app settings menu for Home Screen." (Android 16 CDD). Detecting the current default: `PackageManager.resolveActivity(homeIntent, MATCH_DEFAULT_ONLY)` — "Determine the best action to perform for a given Intent... be sure to consider whether to set the MATCH_DEFAULT_ONLY only flag. You need to do so to resolve the activity in the same way that Context.startActivity(Intent) and Intent.resolveActivity(PackageManager) do" (https://developer.android.com/reference/android/content/pm/PackageManager). The system itself defines "default launcher" as the ROLE_HOME holder: `ShortcutService.getDefaultLauncher()` → "// Default launcher from role manager." `injectGetHomeRoleHolderAsUser(getParentOrSelfUserId(userId))`, and `hasShortcutHostPermissionInner` returns `defaultLauncher.equals(packageName)` (https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/services/core/java/com/android/server/pm/ShortcutService.java).

**Implication.** Use `RoleManager.isRoleHeld(ROLE_HOME)` for the "you are/aren't default" banner and `createRequestRoleIntent` for the request; fall back to `ACTION_HOME_SETTINGS` on API < 29 or if the role is unavailable. Shortcut/private-space APIs only work while you hold ROLE_HOME.

### A4. Splash screens on Android 12+

**Docs.** The system splash screen is shown on cold and warm starts, not hot starts; themed via `windowSplashScreenBackground`, `windowSplashScreenAnimatedIcon`, `windowSplashScreenAnimationDuration`, `windowSplashScreenIconBackgroundColor`, `windowSplashScreenBrandingImage`, and `windowSplashScreenBehavior=icon_preferred` (Android 13+) (https://developer.android.com/develop/ui/views/launch/splash-screen). Android 12: "the system applies a default splash screen on cold and warm starts for all apps constructed from the launcher icon and theme windowBackground" (https://developer.android.com/about/versions/12/behavior-changes-all).

**What the framework does for the *home* activity** (`ActivityRecord.getStartingWindowType`, https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/services/core/java/com/android/server/wm/ActivityRecord.java): `final boolean isActivityHome = isActivityTypeHome(); if ((newTask || !processRunning || (taskSwitch && !activityCreated)) && !isActivityHome) { return STARTING_WINDOW_TYPE_SPLASH_SCREEN; }` and later `if (!isActivityHome) return STARTING_WINDOW_TYPE_SPLASH_SCREEN;` — i.e. the home activity never gets a splash-screen starting window. A task-snapshot starting window is used for home only in one case: "The snapshot of home is only used once because it won't be updated while screen is on... Only use snapshot of home as starting window when unlocking directly." For apps *launched by* the launcher: `shouldUseSolidColorSplashScreen` → `else if (mLaunchSourceType == LAUNCH_SOURCE_TYPE_HOME || launchedFromUid == Process.SHELL_UID) { return !newTask; // only show icon for new task }`; `ActivityOptions.setSplashScreenStyle(int)` (API 33) can force icon/solid colour (https://developer.android.com/reference/android/app/ActivityOptions).

**Implication.** No splash theming is needed for the home activity itself; make `windowBackground` match the home background so cold starts after a kill are not jarring. Apps you launch into a new task will show their icon splash unless you pass `setSplashScreenStyle(SPLASH_SCREEN_STYLE_SOLID_COLOR)`.

## B. Enumerating, launching and managing apps

### B1. LauncherApps vs PackageManager

**Class doc** (https://developer.android.com/reference/android/content/pm/LauncherApps): "Class for retrieving a list of launchable activities for the current user and any associated managed profiles that are visible to the current user, which can be retrieved with getProfiles(). This is mainly for use by launchers. Apps can be queried for each user profile. Since the PackageManager will not deliver package broadcasts for other profiles, you can register for package changes here. To watch for managed profiles being added or removed, register for the following broadcasts: Intent.ACTION_MANAGED_PROFILE_ADDED and Intent.ACTION_MANAGED_PROFILE_REMOVED. Note as of Android O, apps on a managed profile are no longer allowed to access apps on the main profile."

**Implication.** Use `LauncherApps` (not `PackageManager.queryIntentActivities`) so that work/private profiles and cross-profile package callbacks work, and so launches use `startMainActivity` with the right `UserHandle`.

### B2. Package visibility (Android 11+): does a launcher need QUERY_ALL_PACKAGES, and does LauncherApps honour `<queries>`?

**Doc text.** "When an app targets Android 11 (API level 30) or higher, the system filters package information by default" — affected methods include `queryIntentActivities()`, `getPackageInfo()`, `getInstalledApplications()`; "In rare cases where the <queries> element doesn't provide adequate visibility, you can use the QUERY_ALL_PACKAGES permission... If publishing on Google Play, this permission is subject to approval" (https://developer.android.com/training/package-visibility). Automatic visibility covers your own app, certain system packages, the installer, apps that start your activity via startActivityForResult, bound services, content providers you access, and IME clients; the page has **no** exemption for home/launcher apps or role holders (https://developer.android.com/training/package-visibility/automatic). Declaring: `<queries><intent>` requires exactly one `<action>`, cannot use `path*`/`port`/`mimeGroup`, and QUERY_ALL_PACKAGES is described for "Accessibility apps, Browsers, Device management apps, Security apps, Antivirus apps"; "request the smallest amount of package visibility necessary" (https://developer.android.com/training/package-visibility/declaring). The use-cases page has no launcher section but shows `<category>` inside a `<queries><intent>` for the browser case (https://developer.android.com/training/package-visibility/use-cases).

**What the framework does** (primary source = AOSP):
- `LauncherAppsService.queryActivitiesForUser` → `final int callingUid = injectBinderCallingUid(); long ident = injectClearCallingIdentity(); ... queryIntentLauncherActivities(intent, callingUid, user)` → `mPackageManagerInternal.queryIntentActivities(intent, type, MATCH_DIRECT_BOOT_AWARE | MATCH_DIRECT_BOOT_UNAWARE, callingUid, user.getIdentifier())`. The **caller's UID is passed as the filtering UID**, so `LauncherApps.getActivityList` *is* subject to the caller's package-visibility rules (https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/services/core/java/com/android/server/pm/LauncherAppsService.java).
- `AppsFilterBase.shouldFilterApplicationInternal` returns "not filtered" when: filtering is globally disabled; caller appId == target appId; the calling package is disabled for the feature (`!mFeatureConfig.packageIsEnabled(pkg)` — packages that do not target API 30+); or `requestsQueryAllPackages(pkg)`; then the targeted checks (force-queryable, `<queries>` package/intent/provider matches, implicit interactions) apply (https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/services/core/java/com/android/server/pm/AppsFilterBase.java). `AppsFilterImpl` contains no role/home/launcher exemption; force-queryable status is for system-signed/system packages and `config_forceQueryablePackages` (https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/services/core/java/com/android/server/pm/AppsFilterImpl.java). **Holding ROLE_HOME grants no automatic visibility.**
- `<queries><intent>` matching includes categories: `AppsFilterUtils.matchesIntentFilter` → `intentFilter.match(intent.getAction(), intent.getType(), intent.getScheme(), intent.getData(), intent.getCategories(), "AppsFilter", true, ...) > 0`, evaluated only against exported components (https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/services/core/java/com/android/server/pm/AppsFilterUtils.java).

**Conclusion.** `<queries><intent><action android:name="android.intent.action.MAIN"/><category android:name="android.intent.category.LAUNCHER"/></intent></queries>` makes every package with an exported MAIN+LAUNCHER activity visible, and `LauncherApps.getActivityList` honours it. QUERY_ALL_PACKAGES is not required for the core list. Gotcha (inferred from `getLauncherActivities`, which enumerates `getInstalledApplications(..., callingUid)` for the synthesized entries): apps with *no* launcher activity stay invisible under the intent query, so they will not appear as synthesized "app details" entries unless you hold QUERY_ALL_PACKAGES — **UNVERIFIED** by testing. Other features needing visibility (e.g. opening a specific package's Play page, `registerPackageInstallerSessionCallback`) need their own `<queries>` entries.

**Play policy.** Policy Center: "Permitted uses involve apps that must discover any and all installed apps on the device, for awareness or interoperability purposes may have eligibility for the permission. Permitted uses include device search, antivirus apps, file managers, and browsers." Launchers are not named. Invalid: "When the required task can be done with a less broad app-visibility method." "The QUERY_ALL_PACKAGES permission only takes effect when your app targets Android API level 30 or later on devices running Android 11 or later." Developers must "declare this and any other high-risk permissions using the Permissions Declaration Form in Play Console" (https://support.google.com/googleplay/android-developer/answer/10158779). The permissions policy adds: "Apps that have a core purpose to launch, search, or interoperate with other apps on the device, may obtain scope-appropriate visibility to other installed apps" and "You may not use QUERY_ALL_PACKAGES if your app can operate with a more targeted scoped package visibility declaration" (https://support.google.com/googleplay/android-developer/answer/13986130).

**Implication for justa-launcher.** Ship with the MAIN/LAUNCHER `<queries>` intent only (plus targeted entries for Play Store/browser). Do not request QUERY_ALL_PACKAGES for a Play build; if you later want "apps without a launcher activity" or a full uninstall list, treat it as a separate, declared, justified build decision. (Olauncher and Launcher3 both declare QUERY_ALL_PACKAGES; Launcher3 is a system app and Olauncher's Play acceptance is not evidence of policy compliance.)

### B7. Launching and background-launch rules

- `LauncherApps.startMainActivity(component, user, sourceBounds, opts)` (21) for any profile; `Intent.FLAG_ACTIVITY_NEW_TASK` "If set, this activity will become the start of a new task on this history stack." The Context.startActivity note about NEW_TASK from non-Activity contexts was not captured — **UNVERIFIED**.
- Animations: `ActivityOptions.makeCustomAnimation` (16; 4-arg with background colour 33), `makeScaleUpAnimation` (16), `makeClipRevealAnimation` (23), `makeBasic` (23), `setSplashScreenStyle` (33), `setPendingIntentBackgroundActivityStartMode` (34) (https://developer.android.com/reference/android/app/ActivityOptions).
- Background activity launch (BAL): since Android 10 an app may start an activity only if "The app has a visible window, such as an activity in the foreground. The app is the current Input Method Editor (IME). The activity is started from a PendingIntent that was sent by the system (for example, from a notification tap). The app has the SYSTEM_ALERT_WINDOW permission granted by the user. The app has been granted the START_ACTIVITIES_FROM_BACKGROUND permission. The app is bound by a service that has been granted permission to start background activities. The launch is initiated by the device's launcher app, such as when a user taps an app icon or interacts with a widget." Android 14: PendingIntent senders must opt in (`MODE_BACKGROUND_ACTIVITY_START_ALLOW_IF_VISIBLE` recommended); Android 15: creators must opt in; the same rules apply to `IntentSender` (https://developer.android.com/guide/components/activities/background-starts). Android 17 (target 37) extends BAL restrictions to `IntentSender` and asks for migration from `MODE_BACKGROUND_ACTIVITY_START_ALLOWED` to granular modes (https://developer.android.com/about/versions/17/behavior-changes-17).
- When it bites a launcher: starting an activity from a `NotificationListenerService` or `AccessibilityService` callback while the launcher has no visible window (e.g. a gesture recognised by the accessibility service while another app is in front) is a background start and will be blocked; `performGlobalAction` is unaffected because it is not an activity start.

## C. Notification counts ("number in a circle")

### C1. NotificationListenerService essentials

Class doc (https://developer.android.com/reference/android/service/notification/NotificationListenerService): "A service that receives calls from the system when new notifications are posted or removed, or their ranking changed. To extend this class, you must declare the service in your manifest file with the Manifest.permission.BIND_NOTIFICATION_LISTENER_SERVICE permission and include an intent filter with the SERVICE_INTERFACE action. For example:

```xml
<service android:name=".NotificationListener"
         android:label="@string/service_name"
         android:exported="false"
         android:permission="android.permission.BIND_NOTIFICATION_LISTENER_SERVICE">
    <intent-filter>
        <action android:name="android.service.notification.NotificationListenerService" />
    </intent-filter>
    <meta-data android:name="android.service.notification.default_filter_types"
               android:value="conversations|alerting"/>
    <meta-data android:name="android.service.notification.disabled_filter_types"
               android:value="ongoing|silent"/>
</service>
```
The service should wait for the onListenerConnected() event before performing any operations. The requestRebind(ComponentName) method is the only one that is safe to call before onListenerConnected() or after onListenerDisconnected(). Notification listeners cannot get notification access or be bound by the system on low-RAM devices running Android Q (and below). The system also ignores notification listeners running in a work profile. A DevicePolicyManager might block notifications originating from a work profile. From Build.VERSION_CODES.N onward all callbacks are called on the main thread."

API levels: `BIND_NOTIFICATION_LISTENER_SERVICE` 18 (signature); `onNotificationPosted(sbn)` 18, `(sbn, RankingMap)` 21; `onNotificationRemoved` 18/21/26 (with reason); `getActiveNotifications()` 18 ("those that are visible to the current user"), `getActiveNotifications(String[] keys)` 21; `onListenerConnected` 21 ("You are safe to call getActiveNotifications() at this time"); `onListenerDisconnected` 24 ("You will not receive any events after this call, and may only call requestRebind(ComponentName) at this time"); `requestRebind(ComponentName)` 24 ("This method will fail for listeners that have not been granted the permission by the user"); `requestUnbind()` 24 ("The service will likely be killed by the system after this call."), static `requestUnbind(ComponentName)` 34; `getCurrentRanking` 21; `onNotificationRankingUpdate` 21; `cancelNotification(String key)` 21; `snoozeNotification` 26; `migrateNotificationFilter` 31; `META_DATA_DEFAULT_FILTER_TYPES` / `META_DATA_DISABLED_FILTER_TYPES` 31 ("Types provided in this list will appear as 'off' and 'disabled' in the user interface"); `FLAG_FILTER_TYPE_CONVERSATIONS=1`, `ALERTING=2`, `SILENT=4`, `ONGOING=8` (31; ongoing = "important (> IMPORTANCE_MIN) ongoing type notifications"); `REASON_*` 26.

Grant flow: `Settings.ACTION_NOTIFICATION_LISTENER_SETTINGS` (API 22); `ACTION_NOTIFICATION_LISTENER_DETAIL_SETTINGS` (API 30) "Show notification listener permission settings page for app. Users can grant and deny access to notifications for a ComponentName from here... CDD 3.8.3.2: "[C-0-1] MUST correctly and promptly update notifications in their entirety to all such installed and user-enabled listener services".

### C2. What to count and exclude

Ranking (https://developer.android.com/reference/android/service/notification/NotificationListenerService.Ranking): `canShowBadge()` 26 "Returns whether this notification can be displayed as a badge."; `getChannel()` 26; `isAmbient()` 21 ("doesn't require the user's immediate attention"); `isSuspended()` 28 ("the app that posted this notification is suspended, so this notification should be hidden"); `getImportance()` 24; `matchesInterruptionFilter()` 21; `isConversation()` 31; `canBubble()` 29. StatusBarNotification (https://developer.android.com/reference/android/service/notification/StatusBarNotification): `getPackageName()` 18, `getUser()` 21, `getKey()` 20, `getGroupKey()` 21, `isGroup()` 24, `isOngoing()` 18 ("FLAG_ONGOING_EVENT"), `isClearable()` 18 ("either FLAG_ONGOING_EVENT or FLAG_NO_CLEAR"), `isAppGroup()` 30, `getOpPkg()` 29, `getUid()` 29. Notification (https://developer.android.com/reference/android/app/Notification): `number` (API 1) "The number of events that this notification represents... Starting with O, the number may be displayed as a badge icon in Launchers that support badging."; `FLAG_GROUP_SUMMARY` 20; `FLAG_FOREGROUND_SERVICE` 5 ("set for you by Service.startForeground"); `FLAG_ONGOING_EVENT`, `FLAG_NO_CLEAR`; `getBadgeIconType()` / `BADGE_ICON_NONE` ("always show as a number") / `SMALL` / `LARGE` 26; `EXTRA_TITLE`, `EXTRA_TEXT` 19; `CATEGORY_TRANSPORT` 21 (media); `FLAG_PROMOTED_ONGOING` 36 (readable by listeners). `NotificationChannel.canShowBadge()` 26: "Returns whether notifications posted to this channel can appear as badges in a Launcher application. CDD [C-5-1]: a badging launcher "MUST respect the NotificationChannel.setShowBadge() API method".

**How Launcher3 counts** (https://android.googlesource.com/platform/packages/apps/Launcher3/+/refs/heads/main/src/com/android/launcher3/notification/NotificationListener.java?format=TEXT): `notificationIsValidForUI` rejects notifications with `FLAG_GROUP_SUMMARY`; requires the ranking's `canShowBadge()` (false if no ranking available); for the legacy `DEFAULT_CHANNEL_ID` channel rejects `FLAG_ONGOING_EVENT`; rejects when both `EXTRA_TITLE` and `EXTRA_TEXT` are empty; tracks groups via `getCurrentRanking()`; keys notifications per (package, user) with `PackageUserKey.fromNotification`; and calls `requestUnbind` when the system badging setting is turned off. `NotificationKeyData.fromNotification` stores `sbn.getKey()`, `notif.getShortcutId()`, `notif.number` and `count = Math.max(1, count)` (equality by key only) (https://android.googlesource.com/platform/packages/apps/Launcher3/+/refs/heads/main/src/com/android/launcher3/notification/NotificationKeyData.java?format=TEXT). `DotInfo` sums the counts, `MAX_COUNT = 999`, `getNotificationCount() = Math.min(mTotalCount, MAX_COUNT)` (https://android.googlesource.com/platform/packages/apps/Launcher3/+/refs/heads/main/src/com/android/launcher3/dot/DotInfo.java?format=TEXT).

**Recommended filter for justa-launcher (derived from the above):** skip `FLAG_GROUP_SUMMARY`; skip if `!ranking.canShowBadge()` or `ranking.isSuspended()`; skip `FLAG_FOREGROUND_SERVICE`/ongoing media (`CATEGORY_TRANSPORT`) unless the user opts in; count per (package, `sbn.getUser()`) using `max(1, number)` capped at 999; refresh from `getActiveNotifications()` in `onListenerConnected`.

### C3. Play policy for notification access

The current "Permissions and APIs that Access Sensitive Information" page (https://support.google.com/googleplay/android-developer/answer/13986130; the old 9888170 URL now returns 404) has sections for Restricted Permissions, Photo/Video, SMS/Call Log, Location, All Files Access, Package Visibility, Accessibility API, Request Install Packages, Body Sensors, Health Connect, VPN, Exact Alarm, Full-Screen Intent and Age Signals — **no NotificationListenerService-specific section** (searched for "notification listener/notification access"). What applies is the general rule: "restricted permissions are permissions that are designated as Dangerous, Special, Signature, or as documented below... User or device data accessed through Restricted Permissions is considered as personal and sensitive user data. The requirements of the User Data policy apply." The User Data policy requires in-app prominent disclosure that "describe[s] the data being accessed or collected", "explain[s] how the data will be used and/or shared", is "within the app itself", and consent that "require[s] affirmative user action (for example, tap to accept, tick a check-box)" (https://support.google.com/googleplay/android-developer/answer/10144311).

**Implication.** Before sending the user to notification-access settings, show an in-app disclosure ("we read notification metadata only to count unread items per app; nothing leaves the device") with an explicit accept button; keep the count local.

### C4. Android 13+ "restricted settings" (blocks granting notification access / accessibility)

- User-facing: "some device settings may be restricted when you install an app"; to allow: "open the Settings app > Apps > the app > More > Allow restricted settings"; "When you enable restricted settings, you allow apps to get access to sensitive info that could put your personal data at risk. We don't recommend that you allow restricted settings unless you trust the app developer." (https://support.google.com/android/answer/12623953). No developer.android.com page documents the feature (search returned none).
- Trigger in AOSP Android 13 and Android 14 (identical code): `InstallPackageHelper` — "// Apply restricted settings on potentially dangerous packages. if (packageSource == PackageInstaller.PACKAGE_SOURCE_LOCAL_FILE || packageSource == PackageInstaller.PACKAGE_SOURCE_DOWNLOADED_FILE) { enableRestrictedSettings(pkgName, pkg.getUid()); }` which sets `AppOpsManager.OP_ACCESS_RESTRICTED_SETTINGS` to `MODE_ERRORED` for all users (https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android13-release/services/core/java/com/android/server/pm/InstallPackageHelper.java and .../android14-release/...). The source is declared by the *installer*: `PackageInstaller.SessionParams.setPackageSource` — "Optionally indicate the package source of the app being installed. This is informational and may be used as a signal by the system... The default value is PACKAGE_SOURCE_UNSPECIFIED."; `PACKAGE_SOURCE_LOCAL_FILE` "A file manager that is facilitating the installation of an APK file would use this"; `PACKAGE_SOURCE_DOWNLOADED_FILE` "For use in place of PACKAGE_SOURCE_LOCAL_FILE when the installer knows the package was downloaded." (https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/core/java/android/content/pm/PackageInstaller.java).
- Android 15+ (Enhanced Confirmation Mode, `EnhancedConfirmationService.isPackageEcmGuarded`): allow-listed or pre-installed packages are never guarded; otherwise "These install sources are always considered dangerous" — LOCAL_FILE/DOWNLOADED_FILE → guarded; otherwise the package is exempt only if `trustPackagesInstalledViaNonAllowlistedInstallers()` (true when no `<enhanced-confirmation-trusted-installer>` entries are configured), or the *immediate* installer is pre-installed or allow-listed: "ECM doesn't consider a transitive chain of trust for install sources." (https://android.googlesource.com/platform/packages/modules/Permission/+/refs/heads/main/service/java/com/android/ecm/EnhancedConfirmationService.java?format=TEXT). `InstallPackageHelper` (android15-release) comments that `OP_ACCESS_RESTRICTED_SETTINGS` "is used by ECM... as a persistent state denoting whether an app is currently guarded by ECM, not guarded by ECM, or (in Android V+) that this should be decided later."
- The often-reported "Android 14 expansion to session-based installers" is **UNVERIFIED**: the core `InstallPackageHelper` logic is identical in the 13 and 14 release branches and I could not fetch the system PackageInstaller app's code that sets the package source. Whether F-Droid/GitHub-downloaded builds are affected therefore depends on the installer path: browser-download → system package installer (marks downloaded/local file per the API's intent) is restricted; a non-preinstalled store app on Android 15+ is restricted unless the OEM configured it as a trusted installer. Secondary sources (F-Droid issue tracker) report F-Droid-installed apps are affected on 13+; treat as unconfirmed.

**Implication.** For sideloaded/F-Droid builds, expect the notification-access and accessibility toggles to be greyed out until the user does App info > "Allow restricted settings"; build an explicit help flow (open `ACTION_APPLICATION_DETAILS_SETTINGS` and explain the three-dot menu). Play-installed builds are unaffected.

### C5. Reliability, battery, and platform changes affecting the listener

- The system binds the service while access is granted; after `requestUnbind` "The service will likely be killed by the system"; `requestRebind` only works after the user grant. Known disconnects are handled by implementing `onListenerDisconnected` and calling `requestRebind(componentName)` (reference text above).
- Android 15: "Untrusted apps implementing NotificationListenerService are blocked from reading unredacted OTP content in notifications" and notification content is hidden during screen share (https://developer.android.com/about/versions/15/behavior-changes-all) — irrelevant to counting but relevant if you ever display text.
- Android 14: ongoing (`setOngoing(true)`) notifications became user-dismissable except when locked/"Clear all" (https://developer.android.com/about/versions/14/behavior-changes-all) — counts based on ongoing notifications will fluctuate more.
- Android 12: foreground-service notifications may be delayed up to 10 s (https://developer.android.com/about/versions/12/behavior-changes-all).
- Work profile notifications reach a personal-profile listener unless the DPC restricts it (§B4).

To determine if a global action is available, use getSystemActions()" (https://developer.android.com/reference/android/accessibilityservice/AccessibilityService). Declaration (https://developer.android.com/guide/topics/ui/accessibility/service): `<service android:permission="android.permission.BIND_ACCESSIBILITY_SERVICE" android:exported="true">` with `<intent-filter><action android:name="android.accessibilityservice.AccessibilityService"/></intent-filter>` and `<meta-data android:name="android.accessibilityservice" android:resource="@xml/accessibility_service_config"/>`; users enable it under Settings > Accessibility (`Settings.ACTION_ACCESSIBILITY_SETTINGS`, API 5). `BIND_ACCESSIBILITY_SERVICE` is API 16, signature.

Minimal config in practice — Olauncher (https://raw.githubusercontent.com/tanujnotes/Olauncher/master/app/src/main/res/xml/accessibility_service_config.xml): `accessibilityEventTypes="typeViewClicked"`, `accessibilityFeedbackType="feedbackVisual"`, `accessibilityFlags="flagDefault"`, `canRetrieveWindowContent="true"`, `notificationTimeout="10"`, `packageNames="app.olauncher.debug, app.olauncher"` (events limited to its own package). Its service (https://raw.githubusercontent.com/tanujnotes/Olauncher/master/app/src/main/java/app/olauncher/helper/MyAccessibilityService.kt) runs in `android:process=":serviceProcess"`, and on a click event whose source is a `FrameLayout` with a specific content description calls `performGlobalAction(GLOBAL_ACTION_LOCK_SCREEN)` on P+; the recents action is commented out. A pure "action-only" service could set `accessibilityEventTypes` to nothing and `canRetrieveWindowContent="false"` — the guide does not document an explicit "no events" minimum (**UNVERIFIED**).

`isAccessibilityTool` (API 31): "Attribute indicating whether the accessibility service is used to assist users with disabilities... The default is false. Note: If this flag is false, system will show a notification after a duration to inform the user about the privacy implications of the service." (https://developer.android.com/reference/android/R.attr).

**Play policy** (https://support.google.com/googleplay/android-developer/answer/10964491 and the Accessibility section of 13986130): only services "designed to help people with disabilities" may set `isAccessibilityTool=true`; the policy explicitly lists non-qualifying app types: "antivirus software, automation tools, assistants, monitoring apps, cleaners, password managers, and launchers". Non-qualifying apps must complete the Play Console accessibility declaration (purpose, target users, demo video; required since Nov 3 2021 for apps targeting API 31) and "must implement a clear in-app disclosure explaining data access and use, and obtain affirmative user consent"; "The use of the Accessibility API must be documented in the Google Play listing"; "Apps must use more narrowly scoped APIs and permissions in lieu of the Accessibility API when possible"; the API "cannot be used to... Work around Android built-in platform security controls, privacy controls and notifications". Restricted settings (§C4) also block enabling the service for sideloaded builds.

**Implication.** An accessibility service is the *only* public route to lock screen, recents, power dialog, notification shade dismissal and screenshots; keep it optional, off by default, event-free, in its own process, with a prominent disclosure + consent screen, a Play Console declaration and a demo video. Expect review friction; Olauncher's model (accessibility for lock, device admin as fallback) is the current de-facto pattern.

### D2. Alternatives

- **DevicePolicyManager.lockNow()** (API 8; `lockNow(int)` 26): "Make the device lock immediately, as if the lock screen timeout has expired at the point of this call. This method secures the device in response to an urgent situation, such as a lost or stolen device. After this method is called, the device must be unlocked using strong authentication (PIN, pattern, or password). This API is intended for use only by device admins. From version R onwards, the caller must either have the LOCK_DEVICE permission or the device must have the device admin feature... The calling device admin must have requested DeviceAdminInfo.USES_POLICY_FORCE_LOCK to be able to call this method; if it has not, a security exception will be thrown." (https://developer.android.com/reference/android/app/admin/DevicePolicyManager). `USES_POLICY_FORCE_LOCK`: "the device admin must have a "force-lock" tag in the "uses-policies" section of its meta-data" (https://developer.android.com/reference/android/app/admin/DeviceAdminInfo). Enable via `ACTION_ADD_DEVICE_ADMIN` + `EXTRA_DEVICE_ADMIN` (+ `EXTRA_ADD_EXPLANATION`); receiver needs `BIND_DEVICE_ADMIN` (API 8, signature) and `android.app.action.DEVICE_ADMIN_ENABLED`. Deprecation: "Starting with Android 9 (API level 28), some admin policies will be marked as deprecated when invoked by a device admin" (https://developer.android.com/work/device-admin). Olauncher's `policies.xml` is exactly `<device-admin><uses-policies><force-lock/></uses-policies></device-admin>` and `HomeFragment` calls `deviceManager.lockNow()` (repo files above). Gotcha: the "strong authentication" sentence means biometrics do not unlock after `lockNow()` (this is why launchers moved to the accessibility action on P+). Play policy: no device-admin-specific section exists in the permissions policy (**UNVERIFIED** beyond that page); general User Data rules apply.
- **StatusBarManager (hidden).** Source annotations: `expandNotificationsPanel()` "@hide @UnsupportedAppUsage @TestApi" (no `maxTargetSdk`); `expandSettingsPanel()` "@hide @UnsupportedAppUsage"; `expandSettingsPanel(String)` `@UnsupportedAppUsage(maxTargetSdk = R, trackingBug = 170729553)`; `collapsePanels()` `@RequiresPermission(STATUS_BAR)`, `@UnsupportedAppUsage(maxTargetSdk = R, publicAlternatives = "...ACTION_CLOSE_SYSTEM_DIALOGS...")` with the Javadoc "Starting in Android S, apps targeting SDK level S or higher will need STATUS_BAR permission to call this API" (https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/core/java/android/app/StatusBarManager.java). The published non-SDK lists confirm the effective status: Android 16 `hiddenapi-flags.csv`: `Landroid/app/StatusBarManager;->expandNotificationsPanel()V,test-api,unsupported`; `expandSettingsPanel()V,unsupported`; `expandSettingsPanel(Ljava/lang/String;)V,max-target-r`; `collapsePanels()V,max-target-r,test-api` (https://dl.google.com/developers/android/baklava/non-sdk/hiddenapi-flags.csv; identical entries in the Android 15 list https://dl.google.com/developers/android/vic/non-sdk/hiddenapi-flags.csv). Per the restrictions doc, "unsupported" members are "Unrestricted but unsupported and subject to change. Expected to be conditionally blocked in future versions", whereas `max-target-r` members are blocked for apps targeting > 30; blocked access via reflection yields `NoSuchMethodException` (https://developer.android.com/guide/app-compatibility/restrictions-non-sdk-interfaces). The same doc says test APIs are "Included in blocklist since Android 11" — how that interacts with the `test-api,unsupported` double tag is **UNVERIFIED**; empirically Olauncher still calls `expandNotificationsPanel` via `Class.forName("android.app.StatusBarManager").getMethod("expandNotificationsPanel")` (Utils.kt lines 477-479) while holding `EXPAND_STATUS_BAR` ("Allows an application to expand or collapse the status bar", normal). Treat as: works today for all target SDKs, may break in any release, wrap in try/catch and fall back to the accessibility action.
- **Public panels and intents**: `Settings.Panel.ACTION_INTERNET_CONNECTIVITY`, `ACTION_WIFI`, `ACTION_NFC`, `ACTION_VOLUME` (all API 29) "Show a settings dialog containing..." (https://developer.android.com/reference/android/provider/Settings.Panel); `Intent.ACTION_ASSIST` (16), `ACTION_VOICE_COMMAND`, `ACTION_DIAL` (1; "shows a UI with the number being dialed"), `ACTION_SET_WALLPAPER`, `ACTION_SHOW_APP_INFO`; `AlarmClock.ACTION_SHOW_ALARMS` (19), `ACTION_SET_ALARM` (9), `ACTION_SHOW_TIMERS` (26) (https://developer.android.com/reference/android/provider/AlarmClock); `MediaStore.INTENT_ACTION_STILL_IMAGE_CAMERA` / `_SECURE` / `INTENT_ACTION_VIDEO_CAMERA` (https://developer.android.com/reference/android/provider/MediaStore).
- **Torch**: `CameraManager.setTorchMode(String, boolean)` (23) — "Set the flash unit's torch mode of the camera of the given ID without opening the camera device"; no permission is mentioned; "turning on the torch mode may fail if the camera device or other camera resources... are in use"; "If the latest application that turned on the torch mode exits, the torch mode will be turned off."; `turnOnTorchWithStrengthLevel` (33) (https://developer.android.com/reference/android/hardware/camera2/CameraManager).

## E. Screen time on the home screen

- `UsageStatsManager`: "NOTE: Most methods on this API require the permission android.permission.PACKAGE_USAGE_STATS. However, declaring the permission implies intention to use the API and the user of the device still needs to grant permission through the Settings application. See Settings.ACTION_USAGE_ACCESS_SETTINGS. Methods which only return the information for the calling package do not require this permission." `queryUsageStats` (21), `queryEvents(long,long)` (21; "Starting from Android R, if the user's device is not in an unlocked state... null will be returned"), `queryEvents(UsageEventsQuery)` (35), `queryEventsForSelf` (28), `INTERVAL_DAILY/BEST` (21) (https://developer.android.com/reference/android/app/usage/UsageStatsManager). `PACKAGE_USAGE_STATS` protection level "signature|privileged|development|appop|retailDemo" (https://developer.android.com/reference/android/Manifest.permission); `Settings.ACTION_USAGE_ACCESS_SETTINGS` (21). Check grant with `AppOpsManager.OPSTR_GET_USAGE_STATS` (21) via `checkOpNoThrow` (19; 4-arg 36) — `unsafeCheckOpNoThrow` (29) is deprecated in 36 ("Use checkOpNoThrow") — comparing to `MODE_ALLOWED`/`MODE_DEFAULT` (https://developer.android.com/reference/android/app/AppOpsManager). Android 17 minor release 37.2 adds `QUERY_APP_USAGE` ("Allows the holder to query app usage stats"; protection level not extracted — **UNVERIFIED**).
- Play policy: no dedicated usage-access section in the permissions policy page (13986130 headings list); the general sensitive-data rules and User Data disclosure apply; whether the Permissions Declaration Form covers PACKAGE_USAGE_STATS is **UNVERIFIED**. Olauncher ships it with `tools:ignore="ProtectedPermissions"`.

**Implication.** Optional feature behind a disclosure; gate on the app-op check; use `queryEvents` (not daily buckets) if you want accurate per-day foreground time, and handle the locked-device null.

## F. Platform changes affecting launchers (Android 12 → 17)

Items below are from the official behaviour-change pages (paraphrased by the fetch tool; headings are the pages' own). Only launcher-relevant items are listed.

**Android 12 (API 31)** — all apps (https://developer.android.com/about/versions/12/behavior-changes-all): default splash screens on cold/warm starts; "Root launcher activities are no longer finished on Back press"; `ACTION_CLOSE_SYSTEM_DIALOGS` deprecated (SecurityException for target 31); untrusted touch events blocked; FGS notification delay; permission-related PackageManager results filtered by visibility; `Display.getRealSize` deprecated; all apps resizable in multi-window on sw≥600dp. Targeting 31 (https://developer.android.com/about/versions/12/behavior-changes-12): `android:exported` mandatory; PendingIntent mutability; notification-trampoline restrictions; `SCHEDULE_EXACT_ALARM`; foreground-service launch restrictions; app hibernation; custom notification template limits.

**Android 13 (API 33)** — all apps (https://developer.android.com/about/versions/13/behavior-changes-all): `POST_NOTIFICATIONS` runtime permission (only if the launcher posts notifications); FGS task manager; battery resource utilisation; clipboard sensitive flag. Targeting 33 (https://developer.android.com/about/versions/13/behavior-changes-13): granular media permissions (`READ_MEDIA_IMAGES` for any local wallpaper picking); `BODY_SENSORS_BACKGROUND`; media controls from `PlaybackState`; `BluetoothAdapter.enable()` no-op. New for launchers: `ACTION_SHOW_WORK_APPS` (33), per-app languages (`ACTION_LOCALE_CHANGED` extras), `GLOBAL_ACTION_DPAD_*` (33), `Activity.onBackPressed` deprecated, restricted settings for sideloaded apps (not on the dev pages; see §C4). The "intent filters block non-matching intents" item for target 33 was not surfaced by my fetch of the page — **UNVERIFIED**.

**Android 14 (API 34)** — all apps (https://developer.android.com/about/versions/14/behavior-changes-all): exact alarms denied by default; context-registered broadcasts queued while cached; `killBackgroundProcesses` own-app only; "Non-linear font scaling to 200%" (a text-only launcher must test text-size settings against 200% font scale); minimum installable target 23; media owner package redacted unless QUERY_ALL_PACKAGES; non-dismissable notifications become dismissable; system enforces cached-app resource usage. Targeting 34 (https://developer.android.com/about/versions/14/behavior-changes-14): FGS types required; implicit intents only to exported components and mutable PendingIntents must have a component/package; `RECEIVER_EXPORTED`/`RECEIVER_NOT_EXPORTED` required for context-registered receivers (relevant for the profile broadcasts, which are runtime-only); BAL PendingIntent sender opt-in; `TileService.startActivityAndCollapse(Intent)` throws; `USE_FULL_SCREEN_INTENT` limited; zip path traversal; MediaProjection consent. New APIs: `ACTION_PROFILE_ADDED/REMOVED` (34), `requestUnbind(ComponentName)` (34), `ROLE_NOTES` (34).

**Android 15 (API 35)** — all apps (https://developer.android.com/about/versions/15/behavior-changes-all): package stopped state cancels pending intents; widgets disabled on force-stop; private space launcher requirements (§B5); 16 KB pages; minimum target 24; OTP redaction for untrusted listeners; screenshare protection; predictive back animations for opted-in apps; background network access restrictions. Targeting 35 (https://developer.android.com/about/versions/15/behavior-changes-15): edge-to-edge enforced (`windowOptOutEdgeToEdgeEnforcement` opt-out; `setStatusBarColor`/`setNavigationBarColor` deprecated; `layoutInDisplayCutoutMode` must be ALWAYS) — a home screen must handle insets itself; stable configuration (`screenWidthDp` etc. include system bars); `elegantTextHeight` defaults true; TextView width for complex scripts; EditText locale line height; dataSync FGS 6-hour cap; BOOT_COMPLETED FGS restrictions; SYSTEM_ALERT_WINDOW FGS rule; DND via `AutomaticZenRule` only; PendingIntent creator BAL opt-in; `StrictMode.detectUnsafeIntentLaunch`; audio focus only when top/FGS; TLS 1.0/1.1 disallowed. New APIs: `ACTION_PROFILE_AVAILABLE/UNAVAILABLE`, `USER_TYPE_*`, `LauncherUserInfo`, `ACCESS_HIDDEN_PROFILES`, `queryEvents(UsageEventsQuery)`.

**Android 16 (API 36)** — all apps (https://developer.android.com/about/versions/16/behavior-changes-all): JobScheduler quota changes; abandoned-job stop reason; `setImportantWhileForeground` no-op; ordered-broadcast priority scoped to the process; ART internals; 16 KB compatibility mode (`android:pageSizeCompat`); `announceForAccessibility` deprecated; predictive back for 3-button navigation; automatic themed app icons from 16 QPR2 (moot for a text launcher); virtual-device owner overrides; intent-redirection protection (`removeLaunchSecurityProtection()`). Targeting 36 (https://developer.android.com/about/versions/16/behavior-changes-16): edge-to-edge opt-out removed ("windowOptOutEdgeToEdgeEnforcement attribute is deprecated and disabled"); predictive back on by default — `onBackPressed()` not called, `KEYCODE_BACK` not dispatched, temporary opt-out `android:enableOnBackInvokedCallback="false"`; `elegantTextHeight` ignored; `scheduleAtFixedRate` catch-up limited; orientation/resizability/aspect-ratio restrictions ignored on sw≥600dp with the temporary per-activity/app `android.window.PROPERTY_COMPAT_ALLOW_RESTRICTED_RESIZABILITY` property (not honoured at API 37); `MediaStore.getVersion()` per-app; opt-in `android:intentMatchingFlags="enforceIntentFilter"`; health permissions; `NEARBY_WIFI_DEVICES` local-network opt-in; app-owned photos preselected. New APIs: `GLOBAL_ACTION_MENU/MEDIA_PLAY_PAUSE`, `getPrivateSpaceSettingsIntent`, `LauncherUserInfo.getUserConfig`, `FLAG_PROMOTED_ONGOING`, `checkOpNoThrow(4-arg)`.

**Android 17 (API 37)** — all apps (https://developer.android.com/about/versions/17/behavior-changes-all): RAM-based app memory limits (`ApplicationExitInfo.getDescription()` contains "MemoryLimiter:AnonSwap") — keep the resident launcher lean; SMS OTP protection; `usesCleartextTraffic` deprecation plan (wallpaper URLs should be HTTPS or use network security config); implicit URI grants restricted from Android 18; per-app keystore limits; cross-profile loopback blocked; "Restoring default IME visibility after rotation" — the keyboard is no longer restored after unhandled configuration changes unless `android:windowSoftInputMode="stateAlwaysVisible"` or an explicit request (affects the fuzzy-search screen); touchpad relative events; background audio hardening; Bluetooth re-pairing. Targeting 37 (https://developer.android.com/about/versions/17/behavior-changes-17): RemoteViews bitmap memory limit (widgets); lock-free `MessageQueue` (breaks reflection on private fields); `static final` fields unmodifiable via reflection; `ACCESS_LOCAL_NETWORK` runtime permission required for local-network access (a user-pasted LAN image URL would need it); ECH on by default; BAL restrictions extend to `IntentSender`; CT by default; native DCL must be read-only; `setContentCaptureEnabled(false)` no longer disables capture (use `FLAG_SECURE` if needed); large-screen orientation/resizability opt-out removed (mandatory); `BluetoothSocket.read()` returns -1 on close.

**Google Play target-API requirement** (https://developer.android.com/google/play/requirements/target-sdk): from August 31, 2026 new apps and updates must target Android 16 (API 36) or higher (Wear OS/Automotive: API 35; TV/XR: API 34); existing apps must target API 35+ to remain available to new users on newer devices; extensions to November 1, 2026 can be requested; "Permanently private apps" are exempt.

**16 KB page sizes** (https://developer.android.com/guide/practices/page-sizes): "all apps targeting Android 15 (API level 35) and higher must support 16 KB memory page sizes on 64-bit devices on Google Play. Starting February 1, 2027, if your app updates don't support 16 KB memory page sizes, you won't be able to release these updates."; "If your app only uses code written in the Java programming language or in Kotlin, including all libraries or SDKs, then your app already supports 16 KB devices." Check native libs with `zipalign -c -P 16 -v 4 APK_NAME.apk`; Android 16 adds `android:pageSizeCompat`. Relevant only if you pull in a native image decoder or a Rust/C++ core.

**Non-SDK interfaces** (https://developer.android.com/guide/app-compatibility/restrictions-non-sdk-interfaces): lists are blocked / conditionally blocked (`max-target-x`) / unsupported / SDK / test-api; detection via `adb logcat | grep "Accessing hidden"`, `StrictMode.detectNonSdkApiUsage()`, Studio lint and Play pre-launch reports; per-release `hiddenapi-flags.csv` files linked from the page.

## Summary implications for justa-launcher (one line each)

- Manifest: mirror Launcher3's `singleTask` + `clearTaskOnLaunch` + `stateNotNeeded` + `resumeWhilePausing` + empty `taskAffinity` + `exported`, add `excludeFromRecents`, `ACCESS_HIDDEN_PROFILES`, MAIN/LAUNCHER `<queries>`; skip QUERY_ALL_PACKAGES on Play.
- Lifecycle: own Back via `OnBackInvokedCallback`; process is resident at adj 600 and subject to Android 17 memory limiters, so minimise heap; crashes silently un-default you.
- Enumeration: `LauncherApps.getActivityList(null, user)` per `getProfiles()`, cache labels, invalidate on package callbacks and `ACTION_LOCALE_CHANGED`; decide policy for synthesized "app details" entries and multi-activity packages.
- Profiles: runtime-registered receivers for `ACTION_(MANAGED_)PROFILE_AVAILABLE/UNAVAILABLE` (with `RECEIVER_NOT_EXPORTED`), quiet-mode toggle via `requestQuietModeEnabled`, separate private-space container when holding ROLE_HOME.
- Counts: NLS with `default_filter_types`, Launcher3-style filter (drop group summaries, respect `canShowBadge`, skip ongoing/FGS), per-(package,user) `max(1, number)` capped at 999, prominent disclosure before the grant, "Allow restricted settings" help for sideloads.
- Gestures: public intents/panels first; accessibility service (optional, event-free, own process, disclosure + Play declaration) for lock/recents/shade/screenshot; `lockNow()` via device admin as a fallback with the strong-auth caveat; reflection on `StatusBarManager.expandNotificationsPanel` is "unsupported" (works today, may break) and needs `EXPAND_STATUS_BAR`.
- Screen time: optional, gated by the `GET_USAGE_STATS` app-op with an in-app disclosure.
- Compatibility: target API 36 now (37 soon), edge-to-edge insets, 200% font scale, predictive back, large-screen orientation rules, `stateAlwaysVisible` for the search keyboard on Android 17, HTTPS wallpaper URLs.
